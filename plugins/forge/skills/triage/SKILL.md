# Triage

Move issues (and external PRs, which are issues with attached code) through a small state machine. Works with the `gh` CLI on GitHub, or with plain markdown files when there's no tracker.

Every comment or issue body you post during triage starts with:

```
> *This was generated by AI during triage.*
```

Confirm before any write to the tracker (label change, comment, close), unless the user already gave that exact instruction.

## Roles

- **Category** (exactly one): `bug` (something is broken), `enhancement` (new or improved behavior).
- **State** (exactly one): `needs-triage` (maintainer to evaluate), `needs-info` (waiting on reporter), `ready-for-agent` (fully specified for an unattended agent), `ready-for-human` (needs a human: judgment calls, external access, design, manual testing), `wontfix`.

Use the repo's existing label names if they differ (`gh label list`); map them once and state the mapping. Missing labels: propose creating them, don't create silently. Two conflicting state labels on one item: flag and ask.

Transitions: unlabeled -> `needs-triage` -> `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix`. `needs-info` returns to `needs-triage` when the reporter replies. The maintainer can override anytime; flag transitions that look odd.

For a PR: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means ready for a human to merge.

**Without a tracker:** keep one markdown file per item in `issues/` (or the folder the user names) with `Category:` and `State:` lines at the top, and append comments as dated sections.

## What needs attention

Show three buckets, oldest first, with counts and one line per item, tagged `[issue]` or `[PR]`:

1. **Unlabeled:** never triaged.
2. **`needs-triage`:** evaluation in progress.
3. **`needs-info` with reporter activity** since the last triage notes.

```bash
gh issue list --state open --search "no:label" --json number,title,createdAt
gh issue list --label needs-triage --json number,title,createdAt
gh issue view N --comments          # check needs-info items for new replies
gh pr list --state open --json number,title,author,authorAssociation
```

Include only external PRs in discovery (author association not OWNER/MEMBER/COLLABORATOR). A PR the user names explicitly is always triaged. Let the user pick.

## Triage one item

1. **Gather context.** Read the whole item: body, comments, labels, author, dates; for a PR, the diff (`gh pr diff N`). Parse prior triage notes so resolved questions aren't re-asked. Explore the relevant code. Two checks:
   - **Redundancy:** search for an existing implementation by domain concept, not just the request's wording. Report where you looked.
   - **Prior rejection:** read `.out-of-scope/*.md` (if present) and surface any concept match ("night theme" matches `dark-mode.md`).
2. **Recommend** a category and state with reasoning, plus a short summary of the relevant code (including "already implemented" if so). Wait for direction.
3. **Verify the claim.** Bug: reproduce from the reporter's steps (`forge:debugging` Phase 1 if it's hard). PR: check it out (`gh pr checkout N`), run the relevant tests, confirm it does what it claims. Report: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal).
4. **Clarify if needed.** If the request is underspecified, interview the maintainer one round of questions at a time (`forge:brainstorming`), sharpening domain terms and recording decisions as they land.
5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief (below).
   - `ready-for-human`: same structure, plus why it can't be delegated.
   - `needs-info`: post triage notes (below).
   - `wontfix`, by reason:
     - *Already implemented:* point to where it lives. Don't write `.out-of-scope/`.
     - *Rejected bug:* polite explanation, close.
     - *Rejected enhancement (issue or PR):* write/update `.out-of-scope/` (below), link it in the closing comment, close.
   - `needs-triage`: apply the label; optional comment on partial progress.

**Quick override:** "move #42 to ready-for-agent" is an instruction: confirm the exact actions (labels, comment, close) and act, skipping clarification. When moving to `ready-for-agent` without a brief, ask whether to write one.

**Resuming:** if prior triage notes exist, check which questions the reporter answered and present the updated picture before continuing.

## Agent brief

The brief is the contract an unattended agent works from, possibly weeks later. The issue body is context; the brief is authoritative.

- **Durable:** describe interfaces, types, behavioral contracts. No file paths or line numbers; they go stale.
- **Behavioral, not procedural:** what the system should do, not how ("`SkillConfig` accepts an optional `schedule: CronExpression`", not "edit line 42").
- **Testable acceptance criteria,** each independently verifiable.
- **Explicit out-of-scope** to prevent gold-plating.
- For a PR, "current behavior" is the state of the diff, and the brief asks to finish or fix it, reusing what the PR already added.

```markdown
## Agent Brief

**Category:** bug | enhancement
**Summary:** <one line>

**Current behavior:** <what happens now; for a PR, what the diff does and its gaps>
**Desired behavior:** <what should happen, including edge cases and errors>

**Key interfaces:**
- `TypeOrFunction`: what changes and why

**Acceptance criteria:**
- [ ] <specific, testable>
- [ ] <specific, testable>

**Out of scope:**
- <adjacent thing not to change>
```

Bad brief: "The triage thing is broken. Look at the main file around line 150." (vague, stale pointers, no criteria, no scope).

## Needs-info notes

```markdown
## Triage Notes

**What we've established so far:**
- <point>

**What we still need from you (@reporter):**
- <specific, answerable question>
```

Capture everything resolved so far so it isn't lost. Never "please provide more info".

## `.out-of-scope/` records

One file per rejected **concept** (not per issue), kebab-case name (`dark-mode.md`), written as a short readable design note:

```markdown
# Dark Mode

This project does not support user-facing theming.

## Why this is out of scope
<Durable reasoning: scope, technical constraint, or strategic choice. Not "too busy"; that's a deferral, not a rejection.>

## Prior requests
- #42: "Add dark mode support"
```

Flow: existing matching file -> append to Prior requests; else create it. Then comment linking the file and close with `wontfix`. A later match gets surfaced to the maintainer: confirm (append and close), reconsider (delete or update the file, triage normally), or "related but distinct" (triage normally). Only rejected enhancements go here, never built features or bugs.
